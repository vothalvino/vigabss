# FireISP 5.0 — Pre-Launch Test Checklist

Manual / integration tests that only surface against a **real environment or external service** — the mocked-DB jest suite (CI) does not cover these. Mapped from the codebase by a multi-agent audit (2026-07-25).

**Status:** ✅ tested · 🟡 sandbox-only (needs production/real config) · ⚪ unit-only (code path tested, never run for real) · ⬜ untested.  
**Priority:** 🔴 P0 = launch blocker · 🟠 P1 = important · 🟢 P2 = nice-to-have.

> The four you named map as: **SW** + **Finkok** = 🟡 sandbox-tested (stamp AND cancel proven with TEST CSDs — the old Finkok cancel-format defect was resolved by PR #494; still need a *production* PAC contract + a *real* CSD). **WhatsApp** + **Stripe checkout** = ⚪ built & unit-tested, never run against a real provider yet.

## Payments & billing

- [ ] **Stripe hosted Checkout — full round trip (session → pay → webhook → reconcile → invoice paid)**  —  🔴 P0 · ⚪ unit-only
  - **Run:** On a real Stripe test-mode account attached to a payment_gateways row (secret_key_encrypted + webhook_secret_encrypted set), POST /portal/invoices/:id/pay, complete the payment on the real Stripe-hosted page, and let Stripe fire checkout.session.completed to POST /api/v1/payment-webhooks/stripe/:gatewayId. Confirm the pending payment_transactions row (matched by gateway_reference_id = the cs_... session id, or the metadata.transaction_id fallback) flips to succeeded, reconcilePayment marks the invoice 'paid', and the client_balance_ledger credit is written.
  - **Why:** This is the entire online-payment front door and it has never executed against real Stripe — only mocked unit tests. Every link is a silent-failure point: if the session-id UPDATE, the checkout.session.completed→payment_status:'paid' mapping, the webhook secret, or the tenant-scoped transaction match is even slightly off, the customer's card is charged at Stripe but the invoice stays unpaid and the balance never moves, with no error surfaced to anyone.
  - **Needs:** Real Stripe test-mode account + API secret key and webhook signing secret stored on the gateway row (encrypted, ENCRYPTION_KEY set); a publicly reachable webhook URL (Stripe CLI `stripe listen --forward-to` or a tunnel)
- [ ] **Stripe webhook signature verifies over the raw body THROUGH the nginx reverse proxy**  —  🔴 P0 · ⚪ unit-only
  - **Run:** Send a genuinely Stripe-signed event (Stripe CLI or a real dashboard test event) at the production nginx→Express stack and confirm verifyStripeSignature passes. The HMAC is computed over `${t}.${rawBody}`, and rawBody is only captured by the express.json verify hook for /payment-webhooks paths — verify nginx (docker-compose.prod / host-nginx) forwards the byte-exact body, doesn't re-chunk/re-encode/buffer-limit it, and that the Stripe-Signature/Digest headers survive.
  - **Why:** verifyStripeSignature/verifyConektaSignature are byte-exact HMACs. Anything in the real transport that mutates the body (proxy re-serialization, gzip, a body size limit below Stripe's payload, header case-folding) makes every real webhook 401 while unit tests (which hand the function a pristine string) stay green. Result: no webhook ever reconciles in production and the failure is invisible until someone notices invoices never auto-mark paid.
  - **Needs:** Deployed nginx + app stack (docker-compose.prod or host-nginx) and a real Stripe-signed payload (Stripe CLI/dashboard); confirm STRIPE_WEBHOOK_SECRET or per-gateway secret matches
- [ ] **Recurring autopay charges a real saved card off-session (portal enrollment → mandate → unattended charge)**  —  🔴 P0 · ⚪ unit-only
  - **Run:** As a subscriber, click "Enable autopay" on /portal/account → complete the Stripe Checkout SETUP-mode page with a test card → verify the setup webhook stores a recurring_payment_profiles row (pm_ + cus_ + card brand/last4, is_default). Then run process_recurring_charges against real Stripe and verify money actually moves (charged=true, not a perpetual 'pending'), the linked invoice settles via payment_transactions.invoice_id, and DELETE /portal/autopay revokes.
  - **Why:** The whole chain is built (Checkout setup-mode capture collects the SCA mandate; chargeStripe sends customer + off_session=true + payment_method) but has NEVER run against real Stripe — mocks return 'succeeded'. The real-only risks: the setup-mode mandate not actually authorizing the later off-session PaymentIntent (authentication_required decline), the setup webhook's metadata-driven gateway resolution on the env-var route, and the one-active-default unique guard under Stripe's webhook redelivery.
  - **Needs:** Real Stripe test-mode account attached to a payment_gateways row (secret + webhook secret)
- [ ] **Conekta hosted checkout end-to-end (the dominant MX gateway: card + OXXO + SPEI)**  —  🟠 P1 · ⚪ unit-only
  - **Run:** Configure a real Conekta gateway and have a subscriber pay an invoice online: the Pay button must redirect to Conekta's hosted page (POST /orders with an embedded HostedPayment checkout); pay with a test card, then let Conekta fire order.paid (Digest header) to POST /payment-webhooks/conekta/:gatewayId and confirm the tx (matched by the ord_… reference) reconciles and settles the linked invoice. Also try the OXXO cash path (voucher renders; 72h expiry).
  - **Why:** The hosted-checkout flow is built to the Conekta v2 Orders/Checkout spec but has NEVER run against real Conekta — no sandbox account was available. Real-only risks: Conekta's customer_info validation (name/email/phone completeness), the HostedPayment checkout.url actually returning, and the order.paid id matching the stored create-response id. For an MX-focused launch where Conekta is the primary local processor, this is the first thing to prove.
  - **Needs:** Real Conekta account (secret + webhook key) on a payment_gateways row
- [ ] **Duplicate webhook delivery does not double-credit (real provider redelivery / replay)**  —  🟠 P1 · ⚪ unit-only
  - **Run:** Deliver the same succeeded event twice (Stripe auto-retries on any non-2xx, or replay the event id via Stripe CLI / Conekta resend) and confirm webhook_events dedup on (provider, provider_event_id, org_dedup) short-circuits the second one so the ledger is credited once and the invoice is marked paid once.
  - **Why:** Providers redeliver constantly (on timeouts, 5xx, or operator replay). reconcilePayment is best-effort and runs inside handleWebhookEvent; the only guard against double-crediting a client is the webhook_events dedup + the FOR UPDATE lock. That dedup path (org_dedup generated column, migration 417) only ever runs against mocked rows in CI — a real duplicate with a real event id is the only way to prove the partition key and the dedup query actually match and money isn't credited twice.
  - **Needs:** Real Stripe/Conekta account able to redeliver, or manual event replay against a real MySQL (generated org_dedup column must exist)
- [ ] **Refund of a gateway (Stripe/Conekta) payment reverses the invoice + balance**  —  🟠 P1 · ⚪ unit-only
  - **Run:** Take an invoice paid via real Stripe/Conekta online checkout, then refund it (via refund(transactionId) and via a real FULL charge.refunded webhook) and verify: the settled invoice reverts to 'issued', an offsetting 'debit' ledger row is written, the client's computed balance shows the amount owed again, and a PARTIAL refund does NOT reopen the invoice. Redeliver the same charge.refunded and confirm no double-reversal.
  - **Why:** reverseRefund keys off payment_transactions.settled_invoice_id (recorded at reconcile time) and is idempotent, with a full-refund gate on charge.refunded — all built and unit-tested, but the round-trip has never run against a real provider. Real-only risks: Stripe's actual charge.refunded payload shape (refunded/amount_refunded fields on partial refunds) and webhook redelivery timing.
  - **Needs:** Real Stripe/Conekta account (to capture then refund) + real MySQL
- [ ] **Invoice numbering + billing-period generation under real concurrent MySQL**  —  🟠 P1 · ⚪ unit-only
  - **Run:** On a real MySQL (test:db/prod, InnoDB), run the billing cycle concurrently for the same org (parallel generateInvoice / auto_generate_invoices) and confirm invoice numbers are gapless, unique, and never trip the uq_invoices_org_number unique key, and that a billing_period is never double-invoiced.
  - **Why:** nextInvoiceNumber depends on the INSERT IGNORE + `UPDATE ... LAST_INSERT_ID(next_number)+1` sequence idiom and an InnoDB row lock; generateInvoice depends on `SELECT ... FOR UPDATE` on the billing_period. The mocked jest DB cannot exercise row locking, LAST_INSERT_ID semantics, or the unique-key collision at all — so the entire race-safety story is unverified against a real engine. A real concurrency test is the only way to prove two simultaneous billing runs don't 500 on a duplicate invoice number or emit two invoices for one period.
  - **Needs:** Real MySQL/InnoDB (docker-compose.test or prod) with concurrent invocation; not the mocked CI DB
- [ ] **Credit note / refund-as-credit against a stamped invoice produces a stamped CFDI de Egreso**  —  🟠 P1 · 🟡 sandbox-only
  - **Run:** For an MX org, issue a credit note against an already-stamped (vigente) invoice, then stamp it via `POST /credit-notes/:id/stamp` (or the 🧾 Stamp CFDI button on /credit-notes). Verify the CFDI de Egreso (TipoDeComprobante='E', serie egreso, UsoCFDI G02, PUE) is stamped vigente at the PAC, carries `CfdiRelacionados TipoRelacion="01"` with the original invoice's UUID, and downloads/cancels like any CFDI from /cfdi.
  - **Why:** In Mexico, crediting/refunding a stamped ingreso legally requires a stamped egreso CFDI related to the original; without it SAT records overstate income. **Sandbox-proven 2026-07-25** (demo org 5: egreso ABB56BF5… stamped vigente via Finkok sandbox, CfdiRelacionados→ingreso UUID accepted, TFD present; 409/422 guards fired live). Still needs the production repeat with a real CSD.
  - **Needs:** Real PAC contract (SW/Finkok) + real CSD
- [ ] **One-currency-per-org holds across the gateway charge amount, CFDI, and statements (no 'USD' default leak)**  —  🟢 P2 · ⚪ unit-only
  - **Run:** Provision a fresh MXN org and walk a full cycle: generate invoice, record/allocate a payment, run a real Stripe charge, stamp the CFDI, and render the statement PDF — asserting every money surface is MXN and Stripe receives currency:'mxn' with the correct cents.
  - **Why:** payments.currency (and several sibling tables) carry `DEFAULT 'USD'` at the schema level, and past bugs had 'USD' leaking into ledgers/charges. chargeStripe/createStripeCheckoutSession pass currency straight through to Stripe's amount-in-cents — a wrong or defaulted currency means the customer is charged in the wrong denomination (and Stripe may reject MXN-vs-USD zero-decimal assumptions). Config/data drift like this only shows on a clean real org exercised end-to-end through a real processor; the mocked tests never assert the outbound currency Stripe actually sees.
  - **Needs:** Clean org set to MXN + real Stripe test account to observe the charged currency/amount; real MySQL to expose column defaults
- [ ] **Scheduled late-fee / dunning job fires in a real deployment and skips stamped invoices**  —  🟢 P2 · ⚪ unit-only
  - **Run:** In a real deployment with the scheduler/taskRunner running, let apply_late_fees and send_payment_reminders execute on a genuinely overdue invoice (real NOW()/DATEDIFF/timezone) and confirm: the fee lands as a taxable line keeping total = subtotal + tax_amount, invoice_late_fees dedup respects max_applications, and any invoice carrying a vigente/cancel_pending CFDI is left untouched.
  - **Why:** These are switch-cased scheduled tasks (taskRunner) — a seeded task with no running scheduler simply never fires, silently, so late fees are never collected. The date math (DATEDIFF(NOW(), due_date), CURDATE()) is timezone-sensitive and only correct under the server's real clock/TZ, not a mocked one. And the 'skip invoices with a live CFDI' guard is critical: applying a fee to a stamped invoice desyncs it from the document already filed at SAT. Only a real deploy with the scheduler on, a real overdue date, and a real stamped invoice exercises all three.
  - **Needs:** Deployed app with cron/taskRunner enabled + real MySQL + correct server timezone; an overdue invoice and a stamped-CFDI invoice to prove the skip

- [ ] **MX default IVA 16% + per-client Exento resolved into a stamped CFDI**  —  🔴 P0 · 🟡 sandbox-only

- [ ] **CSD upload → encryption-at-rest → decrypt-at-stamp round-trip in real prod**  —  🔴 P0 · 🟡 sandbox-only

## RADIUS & network

- [ ] **PPPoE subscriber auth against a real NAS (Access-Request -> Access-Accept + rate policy)**  —  🔴 P0 · ⬜ untested
  - **Run:** Create a PPPoE contract (subscriberProvisioningService generates creds -> radius row), run the RADIUS sync, then dial a real PPPoE client through a real MikroTik/CHR pointed at FireISP's RADIUS. Confirm Access-Accept, that PAP AND CHAP passwords both authenticate, and that the Mikrotik-Rate-Limit VSA actually shapes the session to the plan speed. Run it BOTH ways: embedded RADIUS server (RADIUS_SERVER_ENABLED=true, radiusServerService.buildAcceptAttributes/generateAttributes) and external FreeRADIUS 3.x reading the synced radcheck/radgroupreply tables (syncFreeradiusTables).
  - **Why:** Every jest test mocks the DB and never emits a UDP packet, so the on-wire VSA encoding (radiusCoaEncoder.encodeVSA length math), PAP/CHAP decode, and plan->attribute mapping have never been parsed by a real NAS. Worse, there are TWO independent attribute writers (embedded generateAttributes vs FreeRADIUS radgroupreply) plus the FreeRADIUS README's own custom authorize queries against the radius table — if they disagree, a subscriber authenticates but is uncapped, gets the wrong speed, or is silently rejected, with nothing in CI catching it.
  - **Needs:** Real MikroTik/CHR NAS with a PPPoE server + a dial-in client; FireISP RADIUS reachable (embedded 1812/1813 or external FreeRADIUS + rlm_sql). Lab CHR (74.208.108.182 / fireisp-nas-3) exists but the dial-in auth path is unverified.
- [ ] **RADIUS accounting ingest (Start/Interim/Stop) from a real NAS into connection_logs**  —  🔴 P0 · ⬜ untested
  - **Run:** Bring a real subscriber online through the NAS and let it send real accounting to FireISP: via the embedded acct server (UDP 1813, radiusServerService.handleAcct) and via the FreeRADIUS rest-module POST (/radius/accounting). Verify connection_logs rows are written, octets+Gigawords combine correctly (combineOctetsGigawords), the Accounting-Request authenticator validates, the session shows online (getActiveSession/getSessionByClientId), and a Stop closes it and rolls up usage.
  - **Why:** Usage totals, data caps, 'who's online', top-talkers, and suspension liveness all derive from connection_logs.   - **Needs:** Real NAS emitting RADIUS accounting; RADIUS_ACCOUNTING_SECRET set (for the FreeRADIUS-rest path) or embedded acct server enabled.
- [ ] **Suspend -> Disconnect-Request actually drops the live session on the NAS**  —  🔴 P0 · ⬜ untested
  - **Run:** With a subscriber online, trigger a suspension (or kickDuplicateSessions) and confirm the RADIUS Disconnect-Request (code 40, to CoA port 3799) actually tears down the live PPPoE session on the real NAS and returns a Disconnect-ACK.

And a UDP timeout is returned as {sent:true}, so FireISP records the disconnect as successful even when the NAS never answered. Only a real DAE listener reveals this.
  - **Needs:** Real MikroTik with RADIUS incoming (CoA/DAE) accept=yes on 3799 and a live session to kill.

  - **Run:** Let an overdue invoice drive walledGardenSuspendContract (CoA sets Mikrotik-Address-List + FreeRADIUS re-sync), confirm the subscriber is redirected to the captive portal by the seeded firewall/NAT rules, record a payment, and confirm walledGardenReconnect (CoA remove + re-sync) restores full service.
